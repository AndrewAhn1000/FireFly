# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

FireFly is a Windows-only desktop tool: an Electron + React UI over a native C++ runtime that captures a game window, turns each frame into typed observations (a UNet segmentation model plus user-defined geometry steps), and records those observations alongside the player's button presses. It is meant to work for any game, so game-specific behaviour lives in user-editable data (flows), not in code.

## Commands

Windows/PowerShell. Prerequisites: Node, Python 3.12 (`py -3.12`), MSVC + CMake ≥ 3.24, git.

**UI**
- `npm run dev` starts Vite on 127.0.0.1:5173. Electron only loads it when `NODE_ENV=development` (`electron/main.cjs`), so in a second terminal run `$env:NODE_ENV='development'; npx electron .`.
- `npm run build` is `tsc --noEmit && vite build` into `dist/`. `tsc` (strict, `noUnusedLocals`) is the only static check; there is no ESLint/Prettier and no renderer test suite.
- `npm start` runs `electron .`, which loads `dist/`, so build first.
- `npm run package` builds and runs electron-builder into `release/` (an NSIS installer, `FireFly-Setup-<version>.exe`); it expects `python-bundle/` (`npm run python:bundle`: embedded Python 3.12 with the lock file's packages, CPU PyTorch, and `..\worker` added to its `python312._pth`, since embedded Python ignores a script's own folder and the workers import each other by name) and a native build. The installer carries `build/native/Release`'s `firefly-runtime.exe`, `firefly-input.exe` and DLLs as `resources/native` (`NATIVE_DIR` in main.cjs), the workers (tests left out) and the Python bundle. `scripts/after-pack.cjs` (electron-builder's `afterPack`) then replaces the packager's Windows user name with as many x's in every packaged file: compilers and pip record build paths (OpenCV's and FireFly's source paths in error messages, every `.pyc`'s source path), about 8,600 of them, which would otherwise ship to everyone. Test a package with `release/win-unpacked/FireFly.exe --user-data-dir=<temp>`, which keeps your real data out of it. Releases are built by `.github/workflows/release.yml` on a `v*` tag (or by hand from the Actions tab): it builds the native runtime with the DirectML ONNX Runtime (`native:onnxruntime:gpu` after the CPU one, so models run on the GPU too), bundles Python, packages and attaches `FireFly-Setup-<version>.exe` to the release.
- **GPU training in the installed app** (`electron/gpu.cjs`): the bundle's PyTorch is the CPU build, so the Train tab offers **Download GPU support**: the CUDA build of the bundle's own torch and torchvision versions (`pip --target`, `--no-deps`, `--progress-bar raw` for progress), into `<userData>/gpu/<build>-<time>` (never into the app, so a failed or cancelled download can't break it and an app update doesn't lose it), used only once a real sum on the card works, recorded in `<userData>/gpu/installed.json`. Training gets it through `FIREFLY_GPU_TORCH` (`pythonEnv` in main.cjs), which `worker/sitecustomize.py` puts first on the bundled Python's path; **Remove GPU support** deletes it. `planFor` picks the build from `nvidia-smi`: the driver's CUDA version and the card's compute capability. PyTorch 2.14's Windows builds are cu126, cu130 and cu132 (no cu124 or cu128); CUDA 13 dropped cards before Turing (7.5), such as the GTX 10 series, so those get cu126; cards under 5.0 have none, and a driver older than CUDA 12.6 (driver 560) is told to get NVIDIA's own driver, since Windows Update usually doesn't install it. The Train tab says in every case that training runs on the CPU without the GPU (it was never required, though the old messages read as if it were), and in a development setup shows the `.venv` pip command for the exact versions and build. `tests/gpu.test.cjs` (`npm run test:gpu`), `tests/gpu-ui.cjs` (`npm run test:gpu-ui`).

**Native runtime** (`native/`, built to `build/native/Release/`)
- One-time: `npm run setup` (`scripts/setup.ps1`) checks the tools (re-reading PATH, and falling back to Visual Studio's bundled CMake), then runs `npm install`, `native:setup` (pins vcpkg into `.tools/`), `native:onnxruntime:gpu`, `native:configure` (a fresh CMake configure), `native:build` and `python:setup`. vcpkg's tool downloads live in `%LOCALAPPDATA%\firefly-vcpkg-downloads`, not TEMP: Storage Sense empties old TEMP files but leaves their folders, which vcpkg takes as the tools still being there; OpenCV needs that path without spaces (its short name is used otherwise). ONNX Runtime goes into `native/libs/`: `native:onnxruntime:gpu` (DirectML, preferred by CMake when present, with `DirectML.dll` copied next to the runtime) or `native:onnxruntime` (CPU only); without either, `segment` nodes fail at runtime. Re-run configure and build afterwards. `python:setup` keeps a CUDA build of PyTorch already in `.venv` rather than swapping it for the lock file's CPU build.
- `npm run native:build`, `npm run native:test` (ctest).
- One test: `ctest --test-dir build/native -C Release -R observation-graph` (or `recording-session`, `template-fit`). Each test binary is a single `main()` that takes no arguments, so there is no per-case filter; cases live in `graph_tests.cpp` and `template_tests.cpp` (`test("...", ...)`) and `session_tests.cpp` (`check(...)`).
- `main.cpp` includes `<windows.h>`, whose `near` and `far` macros break headers it shares with the tests: don't use those as identifiers there (`NOMINMAX` only covers `min` and `max`). A rebuild of `firefly-runtime.exe` needs it not to be running.
- `firefly-graph.exe graph.json [image.png [display.png [preview-node]]]` evaluates a graph offline; with only `graph.json` it prints the observation schema.

**Python** (`worker/`)
- `npm run python:setup` creates `.venv` and installs CPU torch. `npm run test:python` runs everything.
- One file: `.venv\Scripts\python.exe -m unittest discover -s worker -p test_review.py`. One test, from inside `worker/`: `..\.venv\Scripts\python.exe -m unittest test_review.ReviewTests.test_manual_and_automatic_annotations`. Modules import each other by bare name (`from review import ...`), so `worker/` has to be on the path.
- `worker/train_unet.py --data <dir> --out <dir>` is what the Train tab runs, and `worker/check_dataset.py` sanity-checks a dataset. Always use a temp `--out`: `runs/unet` holds a real trained model. Decoding each PNG and resizing it every epoch was most of an epoch's time (25,902 images, about 2 minutes an epoch with the GPU waiting), so `--cache` (the Train tab's “Decode the images once”) decodes what training reads once, at the training size, into raw `.npy` files in `<out>/.decoded` (`SegDataset.cache`, masks as bits, read through memory maps each loader worker opens itself; skipped if the disk hasn't room; a folder left by a run the PC was restarted during is deleted first). They're written in order with ordinary writes, pushed to disk every 512 MB, at below-normal priority: written through a memory map, the writer's memory grew with the whole file (8.2 GB for 5.4 GB of images, against 2.4 GB flat now, and twice as slow), and 50 GB of 800 × 600 images froze a 32 GB PC until it was restarted, and deletes them however training ends: the script in `finally`, and `main.cjs` (`removeDecoded`) after a training it stopped, which it ends with `taskkill /T` so the loader workers go too (Windows doesn't end a process's children with it, and they held the files open). `--workers` (the tab's Workers, 0 = 4 with a GPU, none on the CPU) is passed through for both. The model's input is `--width` × `--height` (the tab's Width × height, steps of 8; `--img-size` is the square they default to, and an older saved `imgSize` becomes both): images are fitted in keeping their proportions, centred, the rest black (`_fit`), as `onnx_node.cpp` fits a game's frames, and the export's input is `[N, 3, height, width]`, which the runtime and `models.cjs` read. The UNet pads a level that doesn't halve evenly (`_pad_to`), so 800 × 600 works as well as 800 × 608. The wz extractor's dataset is 800 × 600 crops at full scale (`preprocess.py --size 800 600`), the v83 client's own size. A script using `multiprocessing` (the decoding pool) needs the `if __name__ == '__main__'` guard on Windows.
- The Train tab also trains a YOLO object detector (its **Segmentation (UNet) / Object detection (YOLO)** switch, `trainConfig.kind`, with the detector's own dataset, output, epochs, batch, model and image size in `trainConfig.yolo`): `worker/train_yolo.py --data <dataset with data.yaml> --out <dir> --weights-dir <dir>` wraps Ultralytics (`ultralytics` in the lock file), printing the same `BATCH:`/`PROGRESS:` lines (progress with `kind: 'yolo'`, precision, recall, `map50`, `map`; `BATCH:` on a fresh line, since Ultralytics' progress bar redraws its line, and main.cjs strips its carriage returns and colours), honouring `pause.flag`, writing `history.json`, and resuming from `<out>/weights/last.pt`. Its output is `weights/best.pt` with Ultralytics' results and plots, exported afterwards (or with `--export-only`, the tab's Export ONNX) to `<out>/best.onnx` at the size it trained at (opset 17, static, `EXPORT_OK:`), which main.cjs adds to Trained Models as a detector (see Flows and models). Ultralytics writes `license: AGPL-3.0` into the export's metadata. Ultralytics downloads the pretrained weights, a font for its plots, and `yolo26n.pt` (its mixed-precision check) into its weights and settings folders, which default to wherever it's first imported, and fixes them on import: the script sets `YOLO_CONFIG_DIR` to `<weights-dir>/config` (it must exist, or Ultralytics falls back to `C:\tmp\Ultralytics`) and changes to the weights folder before importing it, so all of it stays in `<userData>/yolo` (`YOLO_DIR` in main.cjs). Any script that runs Ultralytics with data loader workers needs the `__main__` guard too. `worker/check_yolo_dataset.py` is its Check Dataset (images and boxes per split and class, label problems, classes with few boxes, a grid of samples with their boxes).

Generated and gitignored: `build/`, `dist/`, `.tools/`, `.venv/`, `native/libs/`, `runs/`.

## Architecture

Control flows one way: **renderer (`src/`) → Electron main (`electron/main.cjs`) → native runtime or Python**.

**Renderer ↔ main.** `electron/preload.cjs` exposes `window.bridge`, typed in `src/bridge.d.ts` (change both when adding IPC). Everything about the game goes through one generic call, `bridge.invoke(op, params)`, which main forwards to the native runtime; `runtime:event` carries the runtime's unsolicited events. The model library (`electron/models.cjs`), training and file dialogs have their own channels. `src/App.tsx` is one large component holding nearly all UI state. The settings (Regions, States and their folders, Graphs, the recording setup) are global: one set for whatever window a session is on, loaded once at start (`loadSettings`; switching windows only lets go of what was read, `resetSession`) and kept in localStorage under the scope `SETTINGS` (`{settings}`, in `src/windowSetup.ts`) where a window's title used to go (`firefly-regions-%7Bsettings%7D`, `firefly-states-…`, the States' folders in `firefly-state-folders-…`), so the keys and the file format are as they were. They used to be per window title: the first start with global settings makes the last window's setup (`firefly-last-window`), or else the fullest, the settings, once (`migrateSettings`, flagged by `firefly-settings-migrated`), and leaves the windows' own keys alone. They're shown and edited with or without a session; nothing is saved before they're loaded (`settingsLoaded`), which would write the empty ones the app starts with over them. Memory and Lua States, and Lua Regions, read the game's process, which only a session gives them (the runtime refuses `memory.read` and `memory.run_script` with no target): without one they aren't polled or tested (Run Script is disabled), their rows say “no window” instead of a value, and ending a session drops what they read (`clearProcessReads`). A region that follows its object isn't saved as it moves (see Following an object). A State can be turned off (`GameState.off`, the switch on its row, or a folder's switch for all of its States; locked while recording; `setStatesOff` clears what it showed): it isn't polled (memory read or Lua run), `recordedStates` leaves it out so the runtime doesn't probe or record it, it shows no value whatever its source, and `luaStateDefinitions` sends it with `off: true`, so a script reading `states.Name` fails with “State "Name" is turned off” (`prepareState` in `main.cpp`) rather than running it. Hiding a Region (its eye, `Region.visible === false`) also stops a Lua Region's script and drops its boxes, and `luaRegionSnapshot` marks it `off`, so a script reading it is told it's hidden. A Lua Region's script returns boxes (`{x, y, w, h}`, `{x1, y1, x2, y2}`) or lines (`{ points = {{x, y}, ...} }`, two or more points; `scriptRegionBoxes` in `src/scriptRegions.ts`): a line is drawn through its points, with the Region's name once at its first, and is also the box round it for everything else (its row, templates taken from it, and scripts reading the Region, which get only that box). `tests/script-regions.test.cjs` (`npm run test:script-regions`). States can be kept in folders (`StateFolder`, `GameState.folderId`; **+ Folder**, a row dragged onto a folder as `application/firefly-state` or back to the top level, or the State dialog's Folder; renamed in place, collapsed, and deleting one moves its States out). `tests/state-folders-ui.cjs` (`npm run test:state-folders-ui`). The menu bar at the top (it replaced the toolbar's brand, Record button and connection status, which the status bar shows) has **File › Import Settings…** and **Export Settings…** (`menuOpen` in `App.tsx`; what they did shows in the status bar), with or without a session: Export writes a `.firefly` file (`exportSetup(store, SETTINGS, …)` in `src/windowSetup.ts`, keyed by `{window}` instead of the scope, as files from before settings were global were, so either imports; `electron/setupFile.cjs` adds the trained models ticked, ticked to start with when a State reads their outputs, each with its `.onnx` as base64), and Import shows what one holds (`fileOrigin`: a file from before names its window) and imports the parts and models chosen as the settings (`importSetupFile`, in place of what they were for those parts; models through `importModel`, so one already in the library by its SHA-256 is kept as it is, else given its exported name, threshold, outputs and scores). Nothing in a file names a place on the PC it came from: Dataset Output folders are cleared (`cleared` counts them) and a model's source path, dataset folder and device are left out (`modelMeta`). `tests/setup-file-ui.cjs` (`npm run test:setup-file-ui`). Regions are normalized 0–1 fractions of the frame, while shapes from the runtime are absolute frame pixels.

**Main ↔ runtime protocol** (`native/main.cpp`, one `firefly-runtime.exe` child). Requests are JSON lines on stdin, `{v:1, id, op, ...params}`, up to 64 MB each (`CommandReader`: `template.set` carries every template and mask as base64 PNG, and the old 64 KB limit ended the runtime with a clean exit once a few templates passed it); a longer one is answered `REQUEST_TOO_LARGE` from the id at its start and skipped, and when requests queue up (256), reading waits for room rather than quitting. `main.cjs` logs the runtime's exit code, and every crash it can see, to the terminal and `<userData>/logs/crashes.log` (`logCrash`): the page or another Electron process ending (`render-process-gone`, `child-process-gone`, with reason and exit code) and the window hanging (`unresponsive`); Electron's crash reporter is started with `uploadToServer: false`, so crashes leave dumps in `<userData>/Crashpad` (Windows keeps no report of Electron's crashes, and before this nothing was kept). Replies are length-prefixed packets on stdout: u32 LE length, a kind byte, then the payload, where kind 1 is JSON and kind 2 is a raw frame (u32 id, u32 w, u32 h, f64 capture timestamp, BGRA pixels). Events use `id: 0` plus `event` (`observations`, `recording`, `template.match`, `detection-status`, `capture-error`). Capture runs at up to 60 Hz independently of two bounded latest-frame workers (`latest_worker.hpp`): one evaluates the graph (`detection.cpp`) and one matches templates (`tracking.cpp`), each with its own generation, so neither waits for the other and tracking gets every frame even while recording. A `frame` request returns raw capture immediately, or `{unchanged: true}` when given `since` equal to its capture time (main.cjs sends the live view's last one, so a frame the game hasn't redrawn isn't piped and copied again; main joins stdout chunks only once a packet is whole, since joining each 64 KB chunk copied a frame's megabytes over and over, on the thread that passes observations to play); `processed: true` returns the latest completed processed frame with its source timestamp. Recording submissions target 5–30 Hz (default 15); samples keep their analyzed frame's timestamp and historical button state. Generation checks discard old configuration/target/size results. Windows Graphics Capture only delivers frames when the target repaints, and after 5 s without one the runtime stops capture. See `docs/live-inference.md` for controls, GPU installation and tests.

**Observation graph** (`native/graph.cpp`, `geometry.cpp`, `expression.cpp`, `lua_node.cpp`, `onnx_node.cpp`). An immutable typed DAG compiled from JSON, `{version, id, revision, nodes: [{id, op, inputs, params}]}`, with types number, boolean, vector, image, text and shapes. `publish` nodes are the observations. A node that fails yields an invalid value rather than failing the frame. `segment` runs a UNet ONNX model on CPU or an optional DirectML GPU, with sessions cached by model path, provider, adapter and CPU thread count. The thread count is a runtime setting (`inference.threads`, default 2, the toolbar's Threads selector), deliberately not a graph parameter, since graph parameters are part of the observation schema identity. GPU errors remain visible; switching the Inference selector to CPU recovers. Each op is defined in three places that must stay in agreement: validation and evaluation in `graph.cpp`, and the UI catalogue `OPS` in `src/flows.ts` (a step whose UI differs from its native op, such as `color` → `threshold`, maps through `OpSpec.native`). `crop` can take fractions of the frame (`unit: "fraction"`), so a region reads the same part of it at any window size.

**Flows and models** (`src/flows.ts`, `src/models.ts`, `electron/models.cjs`). A trained model is a UNet exported to ONNX (`image` → `logits`), checked on import and stored under `<userData>/models/<uuid>/`. Its flow is a user-editable set of named outputs, each a chain of generic steps that starts from the mask. `compileFlow` turns a flow into graph nodes and `liveGraph()` wraps it (frame → segment → flow → annotated display). Outputs with `record: true` are published as observations, which is what States and recordings see. Any number of models can run at once (`runningModelIds` in `App.tsx`, in the order they were run, and `modelLives`, each one's feedback; `runModel` adds one, `stopModel` takes one out, both through `setRunningModels`): `liveGraph(models, …)` puts them all in one graph, each model's steps after the one before, its first drawing over what the models before it drew, so every frame goes through each in turn and their times add up. With one model running its steps keep their plain names (`mask`, `detect`, `objects.0`…), since node names are part of the observation identity and recordings made with it must stay valid; with several, each model's are prefixed with its key (`modelPrefix`: `m<8 hex of its id>.`), and the app reads each model's own results back by its flow's names (`ownNodes`, also for its previewed step). Each model can run on its own device (`TrainedModel.device`, `cpu` or `directml:<adapter>`, saved through `models.update`; absent follows the toolbar's Inference, the **Runs on** choice in Trained Models, `setModelDevice` in `App.tsx`, which moves a running model at once and puts it back with a notice if the graph won't apply there): `liveGraph` gives each model's `segment`/`detect` its `modelInference`, so it's part of the observation identity as the toolbar's choice is, and the toolbar's Threads shows while any model may run on the CPU. Recorded names are shared: `compileLive` compiles the running models in order, so a later model's output named like an earlier one's isn't recorded (the Trained Models tab says so on the later one). States reading a model read every running model's observations, and Detected area is the first segmentation model's. A graph may have up to 256 nodes and 256 KB (it was 64 and 60 KB). `tests/multi-model-ui.cjs` (`npm run test:multi-model-ui`) runs `runs/unet` and `runs/yolo/first` together. Game-specific logic, such as separating platforms from ladders, is a flow template tuned to the masks of the sibling `wz extractor` project. It is deliberately not native code. A model can also be a YOLO **detector** (`TrainedModel.kind: 'detector'`, `classes`): `models.cjs` recognises one on import (`detectorInput`: one [N, 3, H, W] input, a [1, 4 + classes, anchors] or end-to-end [1, n, 6] output, class names from the ONNX metadata Ultralytics writes, `inspectOnnx` reading `metadata_props`), keeps its mAP from `history.json`, and its threshold (0.25) is the least confidence a box needs (the Outputs tab's Confidence). The native `detect` op (`detectOnnx` in `onnx_node.cpp`, the same cached sessions, CPU or DirectML) letterboxes the frame to the model's input with grey 114 as Ultralytics does, decodes the boxes, and keeps the best of overlapping ones per class (NMS, IoU 0.7, at most 300); each box is a shape with its four corners and props `x, y, w, h, cx, cy, area, confidence, class` in frame px, so `filter` and the shape functions read it. `liveGraph` runs `detect` and a `filter` per class (`class.<i>`, `class == i`) instead of `segment`, a detector's flow starts from those (`detectorRoots`: `detections`, `class:<i>`, "All detections" and "Class: <name>" in the Outputs tab), and its default flow (`detectorFlow`) records and draws each class as “<class> (detected)”; it has no Detected area. `tests/detector-ui.cjs` (`npm run test:detector-ui`) imports `runs/yolo/first/best.onnx` and runs the applied graph through `firefly-graph.exe` on a dataset image.

**Values read from regions.** A region can carry its own flow (`Region.flow`, saved with the region and edited in the Values tab through the same `FlowEditor` the model Outputs tab uses). Its outputs start from the region's pixels, a fractional `crop` of the frame, instead of a model mask, and read things like a bar's fill (`color` → `reach`). `compileLive()` compiles the model's flow and every region's together so recorded names can't clash, and `liveGraph()` includes both, so region values work with no model running and are recorded in each sample. Observations reach the UI as `streamLive` whether or not a model runs. The graph is re-applied when a region's box or flow changes, and while recording that waits until the recording stops. A region that follows an object (template matching) is left out, because the graph's crop is fixed per applied graph.

**Reading text (OCR).** The `ocr` op turns an image, or a mask of the letters, into a text value, and `number_in_text` takes the Nth number out of text (`1,234` is one number, and a minus counts only at the start or after a space or `(`). In the UI they are the "Read text" and "Find a number" steps and the "Text (OCR)" and "Number (OCR)" region templates; `RegionTemplate.result` says what a template's value is, so the New State dialog makes a `text` state for the first. `native/ocr_node.cpp` is portable: it prepares the image (grayscale, dark text on a light ground by which tone is the minority, contrast stretch, enlarged until the text is about 48 px tall, a light border), caches a read by a hash of the pixels, reads a changing image at most every 250 ms per node (`ocrPacing()`, with an injectable clock), tries an empty read again at the neighbouring sizes, and with `accuracy: "careful"` takes the majority over five sizes. The recognizer is a hook (`setTextRecognizer`), so `graph_tests.cpp` runs the node with a fake one. `ocr_windows.cpp` (the `firefly-windows-ocr` library, installed by `firefly-runtime` and `firefly-graph` through `installWindowsOcr()`) implements it with `Windows.Media.Ocr`, which needs an OCR language in Windows (Settings › Time & language › Language & region; a missing one is reported on the step). On small UI text drawn in Tahoma 11–13 px it reads about 80% of lines exactly (85% careful) at a few milliseconds a read; `/` read as `1`, changed case and dropped spaces are the usual misses, and text isolated with Pick a colour → Clean up reads better. Recordings keep text observations, but the policy trainer leaves text (and images) out. Runtime JSON is written with the `replace` error handler, because text from the screen must never make a `frame` reply throw and end capture.

**Following an object.** "Follow the object in this box" sends the region's templates with `template.set` (`{region, context, templates, ...}`; `template.remove {region}` and `template.clear` undo it). Any number of regions can follow their objects at once: the runtime keeps a `Track` per region, and on every frame the tracking worker (`Tracker` in `tracking.cpp`) matches all of them in that one frame, converting and shrinking it once for all. It emits one `template.match` event per frame, `{timestamp, width, height, durationMs, regions: [{region, context, found, confidence, x, y, w, h, ...}]}`. A region's failure is reported in its own entry (`error`) without costing the others their results. `App.tsx` keeps per-region state (`trackedIds`, `templateContextsRef`, `trackConfs`, `templateSnapshots`, `templateMatchBoxes`) and ignores a result whose context isn't the region's current one. Each region has a threshold, the least confidence a match needs (`Region.matchThreshold`, a 0–100% slider in the region editor, read through `matchThreshold()`: 45% by default following one object, 75% multi-match or corners), sent as `threshold` in `template.set`. For one object the runtime reports its best place's `confidence` even under the threshold, with `found: false`, so the confidence bar (which marks the threshold) shows what scenery and missed poses score. It also reports `detected`: every template that wins a place of its own at or above the threshold (the box follows the first). Template states read these, so several states of one region can be true at once; two templates at the same place still count once, for the stronger. Template states don't flicker, and don't lag either: the two causes are handled where they happen. Following one object, the template that won it last frame (`History.winner`) keeps it unless another scores `kStick` (0.05) higher at the same place (`Preference` in `matchTemplates`; confidences are unchanged), so two poses that match about as well don't swap frame to frame. Only a near-tie for the best place is settled this way: the preferred template's best place elsewhere never wins, since that moved the box onto a lookalike, where the search then stayed. A frame the object isn't found in at all keeps every template state of the region as it was for up to 500 ms (`LOST_HOLD_MS` in `templateMatching.ts`, `kLostHoldMs` in `tracked.cpp`), since not recognising it says nothing about which template it is; multi-match finding none is an answer and isn't held. A settle time (`GameState.settleMs`, the “Ignore changes shorter than” slider) can still make every change wait, but defaults to 0 (`TEMPLATE_SETTLE_MS`); it used to be 250 ms and delayed every real change (`settle()` in `templateMatching.ts`, run per result in `App.tsx` into `templateSettledRef`, mirrored by `tracked.cpp`). The region editor outlines the templates matching now. Every entry also carries `position` (the found box's centre, frame px) and `velocity` (px/s, a least-squares slope over the last 100 ms of capture timestamps, restarted after a 250 ms gap or a jump of more than twice the box's size), both null while the object isn't found; the tracker keeps each region's recent path in its `History`. In the app these are the region state values Position and Velocity (`REGION_POSITION`, `REGION_VELOCITY` in `templateMatching.ts`, vector states), read from `regionMotion`. A third, **Every match** (`REGION_MATCHES`, a `collection` state recorded as shapes, tracked value `matches`), is where every match is: a point at the centre of each box in frame px (with `w`, `h`, `confidence`, `templateId`; `templates` can narrow it). With Multi-Match on it's every instance, such as every monster, while Position stays the strongest one; following one object it's that box while found. None is an empty list, not a missing value, so formulas like `nearest(mobs, p)` or `count_within(mobs, p, 150)` read it. The app shows it live from `templateSnapshots` (multi-match) or `regionMotion`. These, and template states, are recorded too: see Recording and the agent pipeline. A result at or above it moves the region's live box (`liveBoxesRef`), not `regions`: regions are saved to localStorage only when created or changed in the region editor. Moving a box by hand, taking its corners, or switching following off writes the box where it is on screen into `regions`. Only the box being moved or resized by hand is held back from its results, and a drag ends on a `mouseup` anywhere in the window, not only over the canvas: a drag released outside the Game View used to stay in progress and silently stop every box following its object. Everything that shows or edits a box goes through `placedAt(region, liveBoxes)`. With a region selected in the Game View (clicked or just drawn), the arrow keys move it one frame pixel and Shift+arrows resize it (right/down grow, left/up shrink, the top-left staying put, down to 4 px and never past the frame's edge), Ctrl making either 10 px, snapped to whole pixels (`nudgeRegion`): it moves on screen through `liveBoxesRef` at once and is saved to `regions` once the keys rest for 300 ms, so a held key doesn't save and re-apply the graph on every repeat; Escape lets go of it, and Left/Right step through frames again (their job with nothing selected). Each result updates refs, and the canvas redraws from them straight away; the React state behind the confidence bars and template states is refreshed at most every 125 ms, by `scheduleTracking`. A region can look only near where its object was last found (`Region.searchReach`, px, or `'window'`; read through `searchReach()`, sent as `reach`, -1 for the whole window, with `hint`, the box on screen, to start from). Following one object, a template is then looked for where its centre is within reach of the last box's centre, or of where it was heading (the box's last velocity, from its `History.path`, times the time since it was found, at most `kGapMs`: `pathVelocity`), the two areas joined (the `area` argument of `matchTemplates`), so an object moving further than its reach between frames isn't lost and one that stops dead is still found; by corners, reach (plus how far it was heading) replaces the fixed 96 px. An object not found within its reach is looked for twice as far, and twice as far again, in the same frame (`further` in `Tracker::follow`: `max(reach, kGrowFrom = 16)` × 2 each time) until it's found or the whole window has been searched, so an object anywhere in the window is found on the frame it's in and its position is only missing when it isn't recognised anywhere; nearest first, so the box goes to the object near where it was rather than to a lookalike further away. This replaced growing the search a step per frame (and, before that, searching the whole window only after 8 frames), which left a position missing for frames while the object was in view. A frame the object isn't found in at all costs a whole-window search plus the smaller ones before it (about 1.3–2× a whole-window search), every frame it's missing; and since nothing limits it to near where it was then, a pose no template covers lets a lookalike above the threshold anywhere take the box. Templates default to the whole window, corners to 96 px, and multi-match always searches everything. Setting or removing one region doesn't reset the others or where their objects were. A whole-template match can only move the box: its size is always the matched template's, so an object that changes size, such as a mini map, keeps its old box. "Resize the box with the object" (`Region.fit`, `Region.corners`) sends patches of the box's top-left and bottom-right corners instead (`role: 'tl' | 'br'`, plus `hint`, the box's top-left, and `largest`, the biggest it can grow to, both as fractions of the frame). `native/template_fit.cpp` finds the top-left corner near where it was (growing as above within the frame, and then anywhere) and then the nearest bottom-right corner right of and below it, and the box stretches between them. Its events carry `found`, and the renderer ignores the box unless it is true. The region editor is the **Region** tab at the bottom (`regionEditor` in `App.tsx`, three columns: the box and its values; its templates, masks and Match on; threshold, search, multi-match and confidence); choosing or drawing a region opens it (`setShowTemplate`), and its ✕ lets go of the region. A template can carry a **mask** (`Template.maskUrl`, a grayscale PNG the template's size, white where a pixel counts; sent as `mask` in `template.set`): only those pixels count (`Pattern::mask`, passed to every `matchTemplate` through `matchScores`, halved with the coarse copy, NaN and infinite scores from flat masked areas taken as no match; a mask keeping everything is none, one keeping under 16 pixels matches nothing), so the ground behind a sprite doesn't count for or against it. Corners have none. OpenCV's masked matchTemplate costs about 0.7 ms a call however few places it scores, so the full-size checks of a masked template's likely places are scored directly (`maskedScoreAt`, over its kept pixels, the same score to within 0.001), while the first look in the smaller copy uses the mask as it is (cheap there); a masked pattern matched only at full size (edges) takes its likely places from a copy with its left-out pixels set to the kept ones' mean (`Pattern::filled`), which adds nothing to the score. Measured on busy scenes with low-detail sprites against the exact masked search over the whole area: the same place 120/120 (whole window, grayscale 118/120), at 2–2.5× the unmasked cost (150 px reach: colour 5.5 ms against 2.6 unmasked and 49 exact; grayscale 2.7 against 1.1 and 16). The filled copy alone for the first look lost low-detail sprites in grayscale (91/120). It's painted in `src/MaskEditor.tsx` (click a template's thumbnail): a magic wand (the area of about the clicked colour, joined to it or everywhere, with a hover preview) and a brush, each leaving out or keeping, and **Leave out the background**, which grows in from the template's edges only from edge pixels in the edge's common colours, since a sprite touching an edge would otherwise be eaten from its own pixels. Fills compare each pixel with the colour they started from, not their neighbour, which creeps across a soft edge into the object. A region's templates can be added, removed and taken again whether or not it follows its object (they're kept, and used once it does), and so can the “Resize the box with the object” choice; threshold, search reach and multi-match show only while following. **Match on** (`Region.matchOn`, sent as `preprocess` in `template.set`; `Look` in `template_match.hpp`) chooses what whole templates and the frame are matched on: `color` (as they are), `gray` (brightness only: a pose recoloured or tinted still matches, measured 0.96 against colour's 0.35 on a red sprite turned blue; one channel, so fastest) or `edges` (gradient strength of a lightly blurred grayscale: outlines, whatever their colour or lightness). The tracker prepares each look's frame once per frame for every region using it (`pyramidFor`), and `patternFor` prepares templates the same way. Measured findings behind `edges`: a template's border has its edges worked out without its surroundings, which cost an identical 28 px sprite 28% of its score, so `patternFor` leaves 3 px out (`Pattern.inset`, with `full` the template's size, from which the box is rebuilt); thin edge lines halve differently depending on which pixel they start on, so the coarse first look missed objects, and edges are matched at full size only (about 20 ms per template through a whole 1280×720 window, against 4.5 colour and 2.7 gray: give edge regions a search reach); lookalikes score higher on edges (about 0.5 against 0.3); no look survives contrast reversing, and none makes up for a pose no template shows (blurring for tolerance only raised lookalikes). Corners are always matched on colour. The region editor's thumbnails show templates as matched (`src/LookThumb.tsx`, with the same edge operator in JS). Matching (`template_match.cpp`) is coarse-to-fine: a `Pattern` is prepared once per `template.set` with a copy halved while its shorter side stays ≥ 10 px, a `Pyramid` halves the frame to match, and each local best found in the small copy is re-scored at full size (`climb`), so confidences are still full-size `TM_CCOEFF_NORMED`; big score maps are split into row bands across cores. The corners have to look the same at every size and the box has to be tight round the object when they are taken (`snapCorners`); multi-match and corners exclude each other, and all calls to `template.set` go through `syncTemplates`.

**Recording and the agent pipeline.** `native/recording.cpp` and `session.cpp` write recordings (observations plus button actions per sample) to `<userData>/data/catalog.sqlite`. Data is stamped with schema identities. The observation identity is a SHA-256 of the graph definition ignoring id, revision and node positions, so editing any node or step parameter changes it, and the action identity covers the button set. Besides the graph's published outputs, a sample holds tracked observations: every State that reads a followed region (Position, Velocity, Template detected), a memory address or a Lua script, named after the state, is sent by `App.tsx` with `observe.tracked` (refused while recording, and sent again just before `record.start`). Memory and Lua States are "probes" in `main.cpp`: read on the main thread as each frame is sent for detection (at most every `probeGapMs`, 30 ms unless the `probes.gap` op sets it, 0..1000: the toolbar's **State reads**, shown while a memory or Lua State exists, saved as `firefly-probe-gap-ms` and sent each time the runtime is ready, `changeProbeGap` in `App.tsx`; each read reruns every probe, Lua included, and while recording reads come only with samples; the game's process opened once per target; each value carries `readAt`, when its read began, and a frame sent within the gap gets the last reads again marked `reused`), carried on the `DetectionJob`, conformed to their type (memory numbers or text; Lua number, boolean, vector as `{x, y}` or two numbers, text, else object), and timed (`probeMs` on the `observations` event). A Lua probe's positions are client-area pixels (or its script size), not the captured frame's, which includes the title bar and borders, so each carries `toFrame` (`{x, y, sx, sy}`: frame x = x + value × sx, from `scriptGeometry` for that frame); Format Dataset places YOLO labels through it (a 26 px title bar shifted every label before). A Lua script reads memory and Lua States by name as `states.Name` (a read-only table like `regions`; `LuaScriptEditor` completes both): the app sends their definitions as `states` with every `memory.run_script` (`luaStateDefinitions` in `luaPolling.ts`), the runtime keeps the last ones for probes as it keeps the regions, and a State is evaluated the first time a script asks for it and kept for the rest of that evaluation (`StateScope` in `main.cpp`: one request, or one probe pass, so every probe sees the same camera). It's the value the script returned, not conformed; nil stays nil, a failing State fails its reader with the State's name, a loop (by name, or a VM already running, since identical text shares one) and a State reading itself (`stateId`, sent by the State dialog) are errors, and Regions a State reads count as read by its reader. `native/tracked.cpp` evaluates the region ones from each `template.match` event (template states settled as in the app) and a sample takes the tracker's result for its own frame: while recording, the frame a sample is taken from is submitted to the tracking worker with `keep` (`LatestWorker::submit(job, true)`: a kept pending job isn't replaced by ordinary ones), and a detection result waits in `receiveDetection` until the tracker has a result at or after its frame, but only while matching keeps up: `trackLatency` is a running average of capture-to-result time, and the wait lasts until about 1.3× that after capture, at most `kTrackWaitMs` = 100 ms, and not at all when it's over `kBehindMs` = 150 ms (matching far behind held every observation the full 100 ms, and a playing policy's reached the guard too old), so both the sample and the `observations` event (which play reads) carry that frame's tracked values; recording samples are scheduled at `nextTick = max(nextTick + 1000/hz, now)`: never more than hz on average, catching up after late frames (“now + interval” rounded 15 Hz down to 12 and a game's 24 frames a second down to 21). A sample needs a new frame, and a window yields one only when it redraws, so a game's frame rate caps the rate, as does the graph's time per frame. The runtime measures `frameHz` and `detectionHz` (`RateMeter`, `native/rate_meter.hpp`, over 2 s) on `detection-status`, and `sampleHz` on the `recording` event; the Recordings tab says under Samples per second what a recording will actually take and why (`rateNote` in `App.tsx`), the stop button shows the live rate, and the list shows each recording's samples per second against its target. Failing that, it holds the latest before it, as the app's States do, for up to 1 s (`TrackedObservations::at`; each held value carries `heldMs`, shown in the Recordings tab, and older is invalid). Matching works on the newest frame and skips frames while busy, above all beside a CPU model, so without holding a large share of samples had no result of their own (the main loop takes tracking results before detection results for this). They join the schema's fields and identity (`observationSchema(graph, trackedDefinitions, trackedFields)`; with none the identity is the graph's alone), and the `observations` event carries them as `tracked`. Recording is set up in the Recordings tab (`recordingSetup` in `App.tsx`, shown by `RecordingsPanel` as its first column; the Inspector has no recording controls): start/stop, samples per second (5..30) and the buttons recorded (both kept with the settings in `firefly-record-setup-…`), and which observations a recording holds, listed as the States under their own names (`recordedStates.observationOf` maps each to the observation it's recorded as) and then any other observation of `observe.fields`, with choices kept with the settings in `firefly-recorded-…` and images unticked by default: the app sends the names to leave out with `observe.recorded` (refused while recording, sent again before `record.start`), the runtime drops them from samples, and `observationSchema(..., excluded)` drops them from the fields and puts the sorted list in the identity. Left-out observations are still observed, for States and play. An invalid recorded observation, such as the player not being found, makes the sample invalid. A sample's buttons count only while the captured window is the one in front (`InputMonitor::focus`, on every input event and a 5 ms timer: `GetForegroundWindow() == target`). The `recording` event carries `focused`, and the app says so on the Game View's REC overlay and in the Recordings tab while the game isn't in front (typically right after pressing Start recording in FireFly). `dataset.list` and `dataset.read` are answered off the main loop, in order, by `Background` in `main.cpp` (a copy of the catalog, which is only its folder; `packet` writes whole packets under a mutex): listing 323 recordings, 22.6 MB of metadata, took about 256 ms there, and a playing policy's frames waited for it (“taking its result 255 ms (the runtime was busy answering dataset.list…)”); the list also takes the graph, tracked definitions and observation definition out in SQLite (`json_remove`) before parsing. `dataset.delete` removes a recording's rows, input events and files (`Catalog::remove`), never the one being recorded; the Recordings tab asks before deleting, one from its page or several ticked in the list (a box per recording, shift-click for a range, a select-all box and **Delete N**, deleted in turn with failures reported; `removeMarked` in `RecordingsPanel.tsx`). `worker/worker.py` (JSON lines over stdio) trains a small behaviour-cloning MLP from recordings and rejects mismatched identities; `worker/observations.py` (`Featurizer`) turns a sample into numbers the same way for training, export and play: numbers, booleans and vectors as they are (a vector as `name.x`, `name.y`), then legacy derived values (`DERIVED_KINDS`: offset, distance, difference, shapes near a vector; still made for old configs, no longer added in the UI), then the user's **formulas** (`worker/formulas.py`); images, text and raw shapes are never values. A formula (`{name, source}`) is a small expression language over observations (backticks for names with spaces) and other formulas: `+ - * / %`, comparisons, `and/or/not`, `a ?? b`, `.x/.y`, vector arithmetic, `x[-k]` (k grid steps earlier, up to 30), math and vector functions, shape functions over `shapes.py` (`nearest`, `below`, `below_ends`, `count_within`...) and `found(x)`. `FormulaSet` parses and type-checks everything up front (number, boolean, vector, shapes; text and images are errors; cycles and name clashes are reported per formula) and a formula must give a number or boolean (one column, `name`) or a vector (`name.x`, `name.y`), so every result fits the dataset. A value that isn't there (an observation not valid, a shape query with nothing to find, no sample k steps back, division by zero) raises `Missing`, and that row is skipped unless the formula falls back with `??` or asks with `found()`. `columns` keeps only the named values, and a value left out isn't worked out (so what it needs being invalid doesn't cost a row). `Worker.dataset` puts every recording on one **fixed time step** (`stepMs`; blank = `suggested_step`: from the mean of the sample intervals near the median, since a step 1 ms off drifts away from the samples, grown 5% at a time until 9 grid points in 10 have a sample, pauses over 4 intervals aside, because detection falling behind now and then left a step matching only the fast stretches with most points gaps, and every row needing earlier steps lost with them: a 50 s MapleStory recording at 24/s with 90–150 ms stretches gave 73 rows at 42 ms): each grid point takes the sample nearest it within half a step (`on_grid`/`held`), else it's a gap. Samples taken more often than the step fill more than one grid, each a fraction of a step later (`phases`, up to 4; rows of all merged in time order, a sample the current one of one row at most), so the ones between one grid's points are rows too: a 45 ms recording on an 89 ms step left half its samples out (395 rows, now 611). Validation is the last quarter of every recording after a 5% gap (`split_sequences`; a recording too short to split trains whole): taking the last recording whole, a correction of only walking, scored every jump and climb as never pressed. A row's buttons are those held at its sample and any the player pressed since the step before (from the recording's raw key events, `Worker._key_events`, not injected ones; `_rows`' `labels`), so a press between two samples, or in a sample another was nearer the time step than, still counts: a sample holds only what was held when its frame was captured, and in one measurement 1–2% of quick presses reached no row (on the user's jump-quest runs, with their 81 ms step and two phases, none did; `worker/test_labels.py`). A row needs its sample's `actions.valid` (the game in front), all its values, the `history` grid rows before it (default 2), and with `actionDelayMs` the buttons that many steps later; the sample's own `valid` flag is not used. What's skipped is counted by reason (`skippedReasons`, shown after Train and Export). `predict` finds the past steps the same way (nearest buffered sample within half a step of `t - k*step`), failing that the newest up to a whole step further back (never nearer, and each step back an older sample than the last): detection in play slower than the step (a 39 ms step with observations 50 ms apart) found nothing two steps back on most frames, and the policy pressed nothing. It raises for a frame it still can't compute; play releases the buttons, counts it (`released`) and keeps the reason (`missed`), which the banner shows. Nothing in it is specific to a game. **Live view.** Because the runtime returns its latest frame on every poll, `electron/main.cjs` dedupes frames by capture timestamp and encodes a PNG for the live image plus a JPEG (at most one per 50 ms) for the 60 s rewind buffer in `src/frameBuffer.ts`. ## Verifying UI changes

UI changes are checked by booting the real app, not with a test suite. Run a throwaway Electron main script from the project root that calls `app.setPath('userData', <tmp>)` (keeping your real library and localStorage out of it) and then `require('electron/main.cjs')`, with `npm run dev` serving the renderer and `NODE_ENV=development` set. Drive the page through `webContents.executeJavaScript` and take screenshots with `capturePage`. The capture target has to keep repainting and must not be occluded, or the runtime drops capture after 5 s. Never kill `electron.exe` by name, since a real FireFly may be running; kill only the PIDs you started. Once other windows cover the test window, Chromium drops OS-level input sent with `sendInputEvent`, so dispatch DOM events (`PointerEvent`, `WheelEvent`) through `executeJavaScript` instead. Vite reloads the page when `App.tsx` or a component changes, which ends the capture session, so script the session setup to repeat.
